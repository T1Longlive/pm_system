# CI/CD 架构全景与选型（学习 / 面试版）

> 性质：**通用学习资料**，不是本仓库的现状交接文档（现状看 `docs/CI-CD现状与补全计划.md`）。
> 整理时间：2026-09-23。资料来源见文末。

---

## 0. 一句话结论

**CI 负责把代码变成不可变制品，CD 负责把制品安全地送到用户面前。**

工具差异（Jenkins / GitHub Actions / GitLab CI / Argo CD）本质上是**语法问题**；架构差异（谁触发部署、谁持有生产凭据、怎么回滚）才是**职责边界问题**。面试官考的是后者。

## 1. 三种交付范式

### A. Push 式（经典 CI/CD）—— 你现在用的就是这种

```
开发者 push
    │
    ▼
CI 平台（云端构建：跑测试 → 构建镜像 → 推 Registry）
    │
    │  SSH / agent，主动连服务器
    ▼
服务器执行：docker compose pull && up -d
```

- **部署由 CI 主动推**。CI 需要持有**生产服务器的凭据**（SSH 私钥 / agent）。
- 优点：简单、直观、单机/少量服务器足够，学习成本低。
- 缺点：CI 手里有生产权限（安全边界差）；集群状态没有自愈能力；手工改了线上配置没人知道。

### B. Pull 式（GitOps）—— K8s 场景的标准答案

```
Git（期望状态）  ←── 监听 ──── 集群内 Agent（Argo CD / Flux）
                                    │
                                    │ 发现不一致就自动纠正
                                    ▼
                              集群实际状态
```

- **部署由集群内的 agent 主动拉**。CI **不需要**任何生产集群凭据，只需要写 Git 的权限。
- 优点：审计天然（每次变更都是 commit）、回滚 = `git revert`、漂移自动纠正、安全边界干净。
- 缺点：主要面向 Kubernetes；要求配置是声明式的；出问题要会看 agent 的同步状态。

### C. 混合式 —— 2026 年主流大厂形态

```
CI：测试 → 构建镜像 → 推 Registry → 更新 Git 里的 manifest（image tag）
                                              │
GitOps Agent：检测到 manifest 变化 → 同步到集群
```

**CI 只改 Git，不碰集群。** 这条界限是整个架构的核心。

| 维度 | Push 式 | Pull 式（GitOps） |
|---|---|---|
| 部署触发方向 | CI → 服务器 | 集群 Agent ← Git |
| CI 是否持有生产凭据 | **是**（最大风险点） | 否，只需写 Git 权限 |
| 回滚 | 重跑部署脚本、指定旧 tag | `git revert`，更快更可审计 |
| 漂移检测 | 无（要自己写巡检） | 原生自带 |
| 适用规模 | 单机 / 少量服务器 / 非 K8s | K8s 多环境多集群 |
| 学习成本 | 低 | 中高 |

## 2. 构建到底放在哪

这是"云平台构建 vs 服务器自己构建"这个选择题的正解：

| 方案 | 谁提供算力 | 优点 | 缺点 | 什么时候选 |
|---|---|---|---|---|
| **云端托管 CI**（GitHub Actions / GitLab.com / Gitee Go / 云效 / Coding） | 平台 | 零运维、弹性、按需付费 | 按分钟计费（**额度有限**）、拉国外依赖慢、访问不了内网 | 默认首选，团队 < 25 人 |
| **自托管 Runner**（Actions self-hosted / GitLab Runner） | 自己的机器 | 内网可达、分钟不花钱、可用内网镜像源 | 要运维 runner 机器、要防污染 | 有内网依赖 / 构建量大到烧钱 |
| **服务器自己构建**（Jenkins 跑在应用服务器上） | **生产服务器自己** | 免费、看起来省事 | 🔴 **构建抢生产资源**（编译 JVM 吃内存/CPU）、污染生产环境、构建失败可能拖垮线上 | **别这么干** |

🔴 **最后一行是重点，也是你亲历过的坑**：构建过程（Maven/Node 全量编译）资源消耗峰值很高，跟生产服务抢同一台机器的内存，结果就是 OOM 雪崩。构建算力必须和生产隔离。

### Jenkins 在 2026 年怎么定位

- **新项目不要选 Jenkins**：免费的是许可证，不是总成本。服务器管理、插件更新、安全补丁、Groovy 流水线维护，一个 DevOps 花 20% 时间在这上面，年成本超过任何 SaaS。
- **还要用 Jenkins 的场景**：内网/air-gapped 环境、多套非 Git 的源码系统、已有庞大 Jenkins 资产迁移成本过高。
- **面试要会答**：Jenkins 的价值是**控制力和 1800+ 插件生态**，代价是维护开销。

## 3. Docker 在整个链路里的位置

```
代码 → [构建] → 镜像（不可变制品）→ [推] → Registry → [拉] → 运行环境
```

三条铁律：

1. **镜像 tag 必须不可变**。用 commit SHA（`a1b2c3d`）或 `sha256:<digest>`，**禁止 `latest`**。你的项目已经做到了（阶段一）。
2. **构建一次，到处推进**。staging 测过的那个镜像，原封不动推到生产。**绝不在每个环境重新构建** —— 那样你测的和你上线的不是同一个东西。
3. **Registry 是单一可信源**。阿里云 ACR / AWS ECR / 自建 Harbor。开启 tag 不可变策略（registry 层面防止覆盖）。

## 4. 按规模分档（对号入座）

### 档位 1：个人 / 3 人以内，无 K8s ← **你在这**

```
Git 平台 CI（云端构建）→ 镜像仓库 → 1~2 台云服务器
                                        ↑
                          docker compose pull && up -d
                          （Ansible 管服务器配置，脚本管部署）
```

| 项 | 选择 |
|---|---|
| CI | Gitee Go / GitHub Actions / 云效（免费额度） |
| Registry | 云厂商个人版容器镜像服务 |
| 部署 | `deploy.sh` + compose，带健康检查 |
| 服务器配置 | **Ansible**（IaC） |
| 监控 | 云平台自带 + 简单探活 |

**这一档的正确补强**（不是上 K8s，而是把基本功补齐）：
- 不可变 tag + 可回滚（✅ 你做了）
- 部署后健康检查，失败自动停（✅ 你做了）
- 单元测试门禁（✅ 你做了）
- 配置漂移检测（🔄 你的 drift-check 在做）
- 日志轮转与磁盘告警
- 密钥不进仓库（🔴 你踩过：ACR 密码被提交）

### 档位 2：4~25 人，成长期

在档 1 基础上加：
- **staging 环境**（与生产隔离，环境对等）
- 分阶段质量门禁：lint → 单测 → 构建 → 集成测试 → 镜像扫描（Trivy/Snyk）→ 部署
- 密钥管理：Vault / 云厂商 Secrets Manager；CI 到云用 **OIDC 短期凭证**代替长期 AK
- 监控三件套 + 告警（Prometheus + Grafana + 日志）
- 开始考虑 K8s（但**不要为了上而上**）

### 档位 3：25+ 人 / 多集群

- **GitOps**：Argo CD（有 UI、企业默认）或 Flux（轻量、平台工程向）。**二选一，别都用。**
- 环境推进：Image Updater 自动更新 dev，staging/prod 走 **PR 审批**
- 渐进式交付：Argo Rollouts / Flagger（金丝雀 + 指标自动回滚）
- 多集群：ApplicationSet / hub-spoke
- 密钥：External Secrets Operator + Vault
- 策略即代码：OPA Gatekeeper / Kyverno

## 5. 面试高频十问（附得分点）

**Q1. CI / 持续交付 / 持续部署的区别？**
- CI：频繁合入主干 + 每次自动验证。重点是**小而频繁的合并**，不只是"跑测试"。
- 持续交付：每个通过的构建**随时可发布**，最后一步由人决定。
- 持续部署：每个通过的构建**自动上线**，无人工闸门。
- 加分句：持续部署的前提是你**真的信任测试套件** + 有**快速自动回滚**，两者缺一就别做。

**Q2. 画一条生产级流水线（90 秒，工具无关）**
```
PR：lint + 单测（2 分钟内反馈）
合并主干：构建镜像（tag=commit SHA）→ 集成测试 → 镜像漏洞扫描
        → 推 Registry → 部署 staging → 冒烟测试
        → 【人工审批】→ 金丝雀/蓝绿发布生产 → 部署后校验
        → 错误率超阈值自动回滚
```
得分点：**快速检查放最前（fail fast）、昂贵扫描放后面但仍阻断、制品不可变、发布有门禁、回滚自动化**。

**Q3. 为什么要"构建一次，到处推进"？**
因为重新构建 = 你上线的不是你测过的那个东西。可复现性、审计（事故能定位到具体 build）、秒级回滚（重部署上一个 digest）。
反例（说出来很减分）：SSH 进生产 `git pull` 然后现场编译。

**Q4. 蓝绿 / 金丝雀 / 滚动怎么选？**

| 策略 | 做法 | 回滚速度 | 成本 | 适用 |
|---|---|---|---|---|
| 滚动 | 逐实例替换 | 中 | 低（K8s 默认） | 无状态、前后向兼容 |
| 蓝绿 | 两套全量环境，切流量 | **最快**（切回去） | 高（双倍资源） | 要求秒级回滚、DB 变更兼容 |
| 金丝雀 | 5%→25%→50%→100% | 中 | 中 | 高风险改动，需要真实流量验证 |
| 特性开关 | 代码全量上线，功能按人群开 | 最快（关开关） | 低 | 解耦"部署"与"发布" |

加分：没人盯着指标看的金丝雀 = 只是个慢速发布。

**Q5. 回滚怎么设计？**
重部署上一个已知良好的 **digest**，而不是"现场重新编译"。配套：数据库迁移必须向后兼容、**特性开关**（不用重新部署就能关掉坏逻辑）、基础设施版本化（IaC/Helm revision 钉在 Git 里）、部署后自动健康校验。
加分：数据不可逆的变更（DROP COLUMN）要做**向前修**，而不是回滚。

**Q6. 数据库迁移怎么做？**
**expand-contract（扩展-收缩）**：先加新字段不动旧的 → 部署双写的应用代码 → 全量切到新结构 → 下一个版本再删旧字段。用 Flyway/Liquibase 管理顺序。**绝不在同一个发布里同时做破坏性 DDL 和依赖它的代码变更。**

**Q7. 密钥怎么管？**
不进代码、不进流水线 YAML、不进镜像。CI 用平台 Secrets；应用密钥运行时从 Vault / Secrets Manager 注入；**优先 OIDC 短期凭证代替长期 AK**；定期轮换（凭据 90 天）；审计访问记录。

**Q8. GitOps 是什么？什么时候不用？**
Git 是期望状态的唯一来源，集群内 agent 持续 reconcile。收益：审计、revert 即回滚、漂移自愈、CI 不碰生产。
**不用 GitOps 的情况**：快速原型（commit-push-sync 比 `kubectl apply` 慢）、需要命令式步骤的场景（数据库迁移）、没有 K8s。

**Q9. 部署和发布的区别？**
部署 = 把版本装进环境（技术动作）；发布 = 功能对用户可见（业务决策）。用特性开关可以"部署但不发布"。

**Q10. IaC 和漂移检测？**
Terraform 管资源供给、Ansible 管服务器配置。幂等性是核心。漂移检测 = 定期把实际状态与代码比对并告警。
加分（你有真实素材）：**写好期望状态 ≠ 线上收敛**。你的 `live-restore` 事件就是证据 —— Ansible 里写了 `live-restore: true`，线上却是 false，无人发现，直到加了定时 drift-check。

## 6. 对照你自己的 pm-system

| 维度 | 你的现状 | 行业对标 |
|---|---|---|
| 范式 | Push 式（Gitee Go → ACR → ECS） | 档位 1 的标准做法，选对了 |
| 制品 | 镜像 tag = commit SHA | ✅ 符合最佳实践 |
| 回滚 | `scripts/rollback.sh` + 不可变 tag | ✅ 有 |
| 质量门禁 | 24 个单测在云端跑 | ✅ 有 |
| 部署安全 | 健康检查 + RestartCount + 稳定性观察 | ✅ 有 |
| 服务器配置 | Ansible + 每日 drift-check | ✅ 超前（很多小团队没有） |
| 构建资源隔离 | 云端构建，不在生产机构建 | ✅ 正确 |

**你这套已经是档位 1 的优良实践。** 剩下的差距不在架构，而在资源约束（1.8 GiB 内存跑两套栈）和工程细节（构建时长额度、密钥轮换）。

**下一步建议（按性价比排序）：**
1. **轮换 ACR 凭据**（已泄露过，这是安全问题，优先级最高）
2. 日志轮转 + 磁盘告警
3. 把 staging 环境做出来（哪怕只是同一台机器上的另一组 compose + 不同端口）—— 这是迈向档位 2 的第一步，也是面试时能讲的"环境推进"素材
4. 镜像漏洞扫描（Trivy，云端流水线里加一步）

**不要急着上 K8s / Argo CD。** 一台 1.8 GiB 的机器上，K8s 控制面本身就吃掉你大半内存。先把单机这条链路的每个环节讲透，比堆工具更能拿分。

## 7. 常见坑清单（带真实教训）

| 坑 | 后果 | 你的经历 |
|---|---|---|
| 用 `latest` 这种移动 tag | 回滚回滚了个寂寞，线上版本不可知 | ✅ 已改为 commit SHA |
| 每次文档改动也触发完整构建 | 构建额度烧光，新代码上不了线 | ✅ 亲历，已加 `[build]` 提交关键字 |
| 生产环境没有健康检查 | 部署了个起不来的版本还以为成功 | ✅ 已补 |
| 在应用服务器上构建 | 编译抢占内存 → OOM 雪崩 | ✅ 亲历（结构性超配 + 冷启动 JVM） |
| 只写期望状态不做漂移检测 | 配置悄悄偏离，无人知晓 | ✅ 亲历（`live-restore` 漂移事件） |
| 密钥进仓库 | 凭据泄露 | ✅ 亲历（ACR 密码被 Web 编辑器提交） |
| 日志无轮转 | 磁盘被日志吃满（见过 3.2 GB 的崩溃日志吗） | ✅ 今天刚见 |
| 一次全量起所有服务 | 内存峰值叠加 | ✅ 已改为分步起 + 每步看内存 |
