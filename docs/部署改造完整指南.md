## 0. 总览

### 0.1 两种模型

| | Pull 模型 | **Push 模型（本项目最终形态）** |
|---|---|---|
| 谁构建 | 服务器自己 `git pull` + `docker compose build` | **云端构建 Docker 镜像** |
| 服务器负担 | 需要 Maven / Node / 完整源码，**每次部署都编译** | **只需 `docker pull`** |
| 部署耗时 | 十几分钟 | **几十秒** |
| 内存峰值 | 编译时冲高（小机器易 OOM） | **几乎为零** |
| 可回滚 | 靠 git 回退代码 | 靠镜像 tag 回退 |

> **一句话**：Push 模型把「构建」这件重活从生产服务器挪走，
> 服务器只负责「运行」。**小配置服务器强烈建议用 Push 模型。**

### 0.2 最终链路

```
  ① 本地 git push
        ↓
  ② Gitee 云端流水线
       ├─ build@docker：构建后端镜像 → 推送 ACR
       └─ build@docker：构建前端镜像 → 推送 ACR
        ↓
  ③ 派发到阿里云主机（Gitee Go runner）
        ↓
  ④ 服务器执行 deploy.sh
       ├─ git reset --hard（同步源码与脚本）
       ├─ docker compose pull（拉镜像，不构建）
       └─ docker compose up -d（起容器）
        ↓
  ⑤ 健康检查通过 → 用户在浏览器访问
```

### 0.3 涉及的三方

| 角色 | 职责 |
|---|---|
| **本地 / 仓库** | 源码、Dockerfile、compose、部署脚本、流水线 YAML |
| **Gitee** | 代码托管 + 云端构建 + 镜像推送 + 主机派发（流水线引擎） |
| **阿里云** | ACR（存镜像）+ ECS（跑容器）+ 安全组（放行端口） |

## 1. 前置条件与账号准备

### 1.1 账号与资源

| 项 | 说明 |
|---|---|
| Gitee 账号 | 需**绑定手机号**，否则无法开通流水线 |
| 阿里云 ECS | **内存建议 ≥ 2G**；本项目的教训是 1.8G 跑两套应用非常紧张 |
| 阿里云 ACR | 容器镜像服务，**个人版免费**，足够用 |
| 服务器环境 | 已安装 Docker + Docker Compose v2（`docker compose` 子命令形式） |

### 1.2 服务器规格的现实约束

改造前先算一笔账：

```
每个 Spring Boot 后端    ≈ 200–400 MiB
每个 MySQL 容器          ≈ 350–400 MiB
每个 Redis               ≈ 10 MiB
每个 nginx               ≈ 3 MiB
系统 + 面板 + runner     ≈ 300–400 MiB
```

**本项目实测**：一套「后端 + MySQL + Redis + nginx」约 **620 MiB**。
两套同时常驻 + 系统开销 ≈ 1.7 GiB。

> ⚠️ **建议**：如果一台服务器要跑多套应用，**内存 4G 起**。
> 2G 能跑起来，但余量极薄（实测可用内存仅 175 MiB），
> 任何一次编译或内存增长都可能触发 OOM。

## 2. 项目侧改造

### 2.1 配置外置化（12-Factor）

**目标**：代码进仓库、密钥不进仓库。

#### 要改什么

**① 把所有随环境而变的配置写成占位符**

`backend/src/main/resources/application.yml`：

```yaml
spring:
  datasource:
    url: ${DB_URL:jdbc:mysql://localhost:3306/pm_system?...}
    username: ${DB_USERNAME:root}
    password: ${DB_PASSWORD:123456}          # 默认值仅供本地开发
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      password: ${REDIS_PASSWORD:123456}
jwt:
  secret: ${JWT_SECRET:change-me-...}         # 生产必须替换
```

**规则**：
- 一律用 `${环境变量:本地默认值}` 形式
- **禁止任何裸明文密码**
- 默认值要保证「不设环境变量也能本地跑起来」

**② 建模板文件 `.env.example`**

与 `application.yml` 的占位符**一一对应**，只放占位值，不放真实凭据：

```dotenv
DB_URL=jdbc:mysql://mysql:3306/pm_system?...
DB_USERNAME=root
DB_PASSWORD=change-me-strong-password
REDIS_HOST=redis
REDIS_PASSWORD=change-me-redis-password
JWT_SECRET=change-me-at-least-32-characters-long-random-string
PM_UPLOAD_DIR=/pm-upload
CORS_ALLOWED_ORIGINS=http://localhost:5173,http://localhost:8081
```

**③ `.gitignore` 排除真实配置**

```gitignore
.env
.env.local
!*.env.example
```

#### ⚠️ 避坑 1：属性名与占位符同名 = 自我引用，启动必崩

**绝不能**这样写：

```yaml
# ❌ 属性名与它引用的占位符同名
CORS_ALLOWED_ORIGINS: ${CORS_ALLOWED_ORIGINS:http://localhost:5173}
```

**现象**：应用启动直接失败

```
java.lang.IllegalArgumentException: Circular placeholder reference
'CORS_ALLOWED_ORIGINS:...' in property definitions
  -> Error creating bean with name 'webConfig'
```

**原因**：Spring 解析 `CORS_ALLOWED_ORIGINS` → 拿到值 `${CORS_ALLOWED_ORIGINS:...}`
→ 又要解析自己 → 死循环。

**修法**：**删掉这一行**，默认值写在 Java 的 `@Value` 表达式里：

```java
@Value("${CORS_ALLOWED_ORIGINS:http://localhost:5173,http://localhost:8081}")
private String corsAllowedOrigins;
```

**为什么其它变量没事**：它们的「配置路径」与「环境变量名」不同名 ——
`spring.datasource.url` ← `${DB_URL}` ✓。

> **自查方法**：递归扫描 yml 所有字符串值，
> 凡是「叶子键名 == 其中引用的占位符名」就是自我引用。

#### ⚠️ 避坑 2：环境不对称 —— 容器里能跑、本地崩

上面那个 bug **在容器里不会暴露**：

- 容器内 `docker-compose` 的 `env_file` 把 `.env` 注入成真实环境变量
- Spring 的**操作系统环境变量优先级高于 `application.yml`**
- 解析时先命中环境变量，**根本走不到那行错误定义**

而本地 IDE 没有该环境变量 → 命中有问题的定义 → 崩。

> **教训**：**`mvn compile` 通过 ≠ 应用能启动。**
> 配置类改动**至少要真正启动一次应用**。

### 2.2 容器化

#### 后端 `backend/Dockerfile`（多阶段）

```dockerfile
# ---------- 阶段 1：构建 ----------
FROM <ACR>/<命名空间>/maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /build
COPY backend/pom.xml ./pom.xml
COPY settings.xml ./settings.xml              # 走国内 Maven 镜像加速
RUN mvn -s ./settings.xml -B dependency:go-offline   # 独立成层，pom 不变则不重复下载
COPY backend/src ./src
RUN mvn -s ./settings.xml -B clean package -DskipTests

# ---------- 阶段 2：运行 ----------
FROM <ACR>/<命名空间>/eclipse-temurin:17-jre AS runtime
ENV TZ=Asia/Shanghai
WORKDIR /app
COPY --from=builder /build/target/*.jar app.jar
RUN mkdir -p /pm-upload
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]   # exec 形式，JVM 才能收到 SIGTERM
```

**要点**：
- 层缓存顺序：`pom` → `settings.xml` → 依赖下载 → `src`（源码变动不触发重新下载依赖）
- **构建上下文是仓库根目录**（需同时访问 `backend/` 和根 `settings.xml`）
- `ENTRYPOINT` 用 **exec 形式**，否则容器收到的信号到不了 JVM，无法优雅停机

#### 前端 `frontend/Dockerfile`

```dockerfile
FROM <ACR>/<命名空间>/node:20-alpine AS builder
WORKDIR /build
COPY frontend/package.json frontend/package-lock.json* ./
RUN npm install --registry=https://registry.npmmirror.com
COPY frontend/ ./
RUN npm run build

FROM <ACR>/<命名空间>/nginx:alpine AS runtime
ENV TZ=Asia/Shanghai
COPY frontend/nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /build/dist /usr/share/nginx/html
EXPOSE 80
```

#### `.dockerignore`（两个目录都要有）

排除 `target/`、`node_modules/`、`dist/`、IDE 目录、`docs/` 等，
减小构建上下文、加快传输。

#### ⚠️ 避坑 3：nginx 用 `$host` 会让同源请求被误判为跨域（403）

`frontend/nginx.conf` 里**必须**用 `$http_host`：

```nginx
location /api/ {
    proxy_pass http://backend:8080/api/;

    # ❌ proxy_set_header Host $host;      —— $host 会剥掉端口
    # ✅ 用 $http_host 原样透传（含端口）
    proxy_set_header Host              $http_host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

**现象**：浏览器访问 `http://<IP>:8081`，所有 `POST /api/**` 返回 **403**（不是 401）。

**原因链**：

```
浏览器   Origin: http://<IP>:8081      Host: <IP>:8081
nginx    proxy_set_header Host $host   ← 端口被剥掉
后端收到                                Host: <IP>
Spring 由 Host 反推自己的 origin = http://<IP>:8080   ← 端口变 8080
→ 端口 8081 vs 8080 不一致 → 判定为跨域 → 白名单不含该来源 → 403
```

> **关键认知（反直觉）**：
> **「经 nginx 同源反向代理就不需要配 CORS」是错的。**
> 浏览器对**非 GET/HEAD 请求（包括同源 POST）也会带 `Origin` 头**，
> 而 Spring 的「同源」判定依赖 Host 头能否还原出浏览器眼中的 origin。
>
> 用 `$http_host` 后，后端算出的 origin 与浏览器一致 → 判定同源 → CORS 不参与。
> **换 IP / 域名 / 端口都无需改配置。**

### 2.3 编排

#### `docker-compose.yml`

```yaml
services:
  backend:
    # 方案 B：镜像来自云端构建产物，不再本地 build
    image: <ACR>/<命名空间>/pm-backend:latest
    container_name: pm-backend
    env_file: [.env]
    environment:
      DB_URL: ${DB_URL}
      DB_PASSWORD: ${DB_PASSWORD}
      REDIS_HOST: ${REDIS_HOST}
      REDIS_PASSWORD: ${REDIS_PASSWORD}
      JWT_SECRET: ${JWT_SECRET}
      TZ: Asia/Shanghai
    volumes:
      - pm-upload:/pm-upload
    depends_on:
      mysql: { condition: service_healthy }    # 等 MySQL 真正可连接
      redis: { condition: service_started }
    restart: unless-stopped
    # 不映射端口：只允许 compose 网络内的 frontend 访问

  frontend:
    image: <ACR>/<命名空间>/pm-frontend:latest
    container_name: pm-frontend
    ports:
      - "8081:80"                              # 对外唯一入口
    depends_on: [backend]
    restart: unless-stopped

  mysql:
    image: mysql:8.0
    container_name: pm-mysql
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_PASSWORD}      # 与后端共用同一个环境变量
      MYSQL_DATABASE: pm_system
    volumes:
      - pm-mysql-data:/var/lib/mysql
      # ⚠️ 建表脚本必须挂这里，见避坑 4
      - ./backend/src/main/resources/db/init.sql:/docker-entrypoint-initdb.d/01-init.sql:ro
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-p${DB_PASSWORD}"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 40s
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    container_name: pm-redis
    command: redis-server --requirepass ${REDIS_PASSWORD}
    volumes:
      - pm-redis-data:/data
    restart: unless-stopped

volumes:
  pm-upload:
  pm-mysql-data:
  pm-redis-data:
```

**设计要点**：

| 要点 | 原因 |
|---|---|
| **只映射前端端口** | Docker 发布端口会**绕过宿主防火墙**（见下），不映射才是可靠隔离 |
| 后端/MySQL/Redis 不映射 | 容器间靠 compose 服务名互访（`mysql:3306`），无需暴露 |
| `depends_on: condition: service_healthy` | 否则后端会比 MySQL 先启动，连不上库 |
| 数据用具名卷 | 容器重建不丢数据；**但删卷 = 删库，务必谨慎** |
| `restart: unless-stopped` | 崩溃自愈；**手动 stop 后不会被自动拉起** |

> **为什么「不映射端口」比配防火墙更可靠**：
> Docker 发布端口时直接往 iptables 的 DOCKER 链插规则，**优先级高于 firewalld/ufw**。
> 也就是说**宿主机防火墙拦不住 Docker 映射出来的端口**。
> 所以对跑容器的服务器，「不开 `ports:`」才是真正的安全边界。

#### ⚠️ 避坑 4：建表脚本必须挂进 `/docker-entrypoint-initdb.d/`

**现象**：容器都起来了，但后端启动即崩、反复重启。

**原因**：MySQL 容器只建「空库」，**不会执行仓库里的建表脚本**。
若项目没有 Flyway / Liquibase，也没配 `spring.sql.init`，
库就是空的 —— 而应用启动阶段往往就要查库（`ApplicationRunner`、
`@EventListener(ApplicationReadyEvent)`），表不存在直接抛异常。

**修法**：利用 MySQL 官方镜像的标准机制（该目录下的 `.sql` 会在
**数据目录为空时**自动执行）：

```yaml
volumes:
  - pm-mysql-data:/var/lib/mysql
  - ./backend/src/main/resources/db/init.sql:/docker-entrypoint-initdb.d/01-init.sql:ro
```

> ⚠️ **只在首次初始化时执行一次。** 若容器此前已启动过（卷里有空库），
> 需先清卷重来：`docker compose down && docker volume rm <项目名>_pm-mysql-data`

### 2.4 部署脚本

#### `scripts/deploy.sh`

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

APP_DIR="/root/pm-system"
BRANCH="${1:-main}"
LOG_FILE="/var/log/pm-system-deploy.log"
LOCK_FILE="/tmp/pm-system-deploy.lock"
BACKEND_CONTAINER="pm-backend"
FRONTEND_CONTAINER="pm-frontend"
ACR_HOST="<ACR 端点>"

log() { echo "[$(date '+%F %T')] $*" | tee -a "$LOG_FILE"; }

# 并发保护：两次部署同时跑会把容器状态搞乱
exec 9>"$LOCK_FILE"
if ! flock -n 9; then
  log "Another deployment is already running, exiting"; exit 1
fi

cd "$APP_DIR"

# 选择 compose 命令
if docker compose version >/dev/null 2>&1; then DC="docker compose"
elif command -v docker-compose >/dev/null 2>&1; then DC="docker-compose"
else log "docker compose is not installed"; exit 1; fi

# .env 存在性校验（缺了容器起不来，不如提前失败）
if [ ! -f .env ]; then
  log "ERROR: .env not found in $APP_DIR"
  log "请参考 .env.example 创建 .env"
  exit 1
fi

log "Starting deployment for branch: $BRANCH"

git fetch origin "$BRANCH"
git checkout "$BRANCH"
git reset --hard "origin/$BRANCH"

# 私有镜像仓库需要先登录；提前检测并给出可执行的提示
if [ ! -f "$HOME/.docker/config.json" ] || ! grep -q "$ACR_HOST" "$HOME/.docker/config.json" 2>/dev/null; then
  log "WARN: 未检测到 $ACR_HOST 的登录记录"
  log "      若 pull 失败，请先执行： docker login $ACR_HOST"
fi

log "Pulling dependency images"
$DC pull mysql redis || true

log "Pulling application images from registry"
$DC pull backend frontend

log "Starting containers"
$DC up -d --remove-orphans --force-recreate

# 健康检查
wait_for_container() {
  local name="$1" retries=12 delay=5 status=""
  for _ in $(seq 1 "$retries"); do
    status="$(docker inspect -f '{{.State.Status}}' "$name" 2>/dev/null || true)"
    if [ "$status" = "running" ]; then log "Container $name is running"; return 0; fi
    sleep "$delay"
  done
  log "Container $name failed to reach running state, status: ${status:-missing}"
  $DC ps | tee -a "$LOG_FILE" >/dev/null || true
  $DC logs --tail=200 backend  | tee -a "$LOG_FILE" >/dev/null || true
  $DC logs --tail=200 frontend | tee -a "$LOG_FILE" >/dev/null || true
  exit 1
}

# ⚠️ 建议两个容器都检查（只查前端会漏报后端崩溃）
wait_for_container "$BACKEND_CONTAINER"
wait_for_container "$FRONTEND_CONTAINER"

log "Container status"; $DC ps
docker image prune -f >/dev/null 2>&1 || true
log "Deployment finished"
```

**每个设计的理由**：

| 写法 | 作用 |
|---|---|
| `set -Eeuo pipefail` | 任一命令失败即退出，不吞错 |
| `flock -n 9` | **并发保护**，避免两次部署互相踩 |
| 校验 `.env` 存在 | 提前失败，好过容器带空配置启动 |
| `git reset --hard` | 确保加载到的是最新 `deploy.sh`（脚本执行中被改写会产生诡异行为） |
| 登录预检 | 把 `Authentication failed` 转成可执行的提示 |
| 健康检查 | 等容器真正 running 才算成功，失败时 dump 日志 |
| `image prune -f` | 回收旧镜像层，避免磁盘越用越满 |

#### `scripts/mirror-base-images.sh`（方案 B 专用）

**用途**：把 4 个基础镜像转存到自己的 ACR。

**为什么需要**：Gitee 云端构建容器**无法访问 Docker Hub**（直连 i/o timeout）。
把基础镜像放到自己的 ACR 后，云端就能拉取 —— 而 ACR 的可达性是已确定的
（我们本来就在往它推镜像）。附带好处：基础镜像来源固定，供应链可控。

**在服务器上执行一次即可**（服务器的 Docker 已配镜像加速，能拉到 Docker Hub 镜像）：

```bash
ACR="<ACR 端点>"; NS="<命名空间>"
for img in maven:3.9-eclipse-temurin-17 eclipse-temurin:17-jre node:20-alpine nginx:alpine; do
  docker pull "$img"
  docker tag  "$img" "$ACR/$NS/$img"
  docker push "$ACR/$NS/$img"
done
```

### 2.5 换行符

#### `.gitattributes`

**必须在仓库根建这个文件**：

```gitattributes
* text=auto eol=lf

*.sh text eol=lf
*.bash text eol=lf
Dockerfile text eol=lf
Dockerfile.* text eol=lf
*.Dockerfile text eol=lf
docker-compose*.yml text eol=lf
*.yml text eol=lf
*.yaml text eol=lf
.dockerignore text eol=lf
.env.example text eol=lf
nginx.conf text eol=lf

*.jar binary
*.png binary
*.woff2 binary
```

**原因**：Windows 上开发、Linux 上构建运行。
若不加约束，`core.autocrlf` 可能把 shell 脚本转成 CRLF，
而 Linux 上的 bash 遇到 CRLF 会直接报错：

```
bash\r: No such file or directory
```

这是容器/CI 场景里非常典型又极难定位的故障 —— **看不见字符，只看到"文件不存在"**。

**自查**：

```bash
# 检查脚本是否纯 LF（CRLF 计数必须为 0）
python -c "d=open('scripts/deploy.sh','rb').read(); print('CRLF:', d.count(b'\r\n'))"
```

## 3. Gitee 侧配置

### 3.1 开通流水线

仓库页 → **流水线** → 按提示开通（需账号已绑定手机号）。
免费额度：单仓库 200 分钟（永久）+ 每月 500 分钟。

### 3.2 凭证管理（存镜像仓库密码）

位置：**右上角头像 → 设置 → 流水线 Gitee Go → 凭证管理 → 新建凭证 → Docker**

字段**只有 4 个**：

| 字段 | 填什么 |
|---|---|
| 凭证名称 | 随便起，如 `aliyun-acr` |
| **docker仓库地址** | **`<ACR端点>/<命名空间>`** ←⚠️ 见避坑 5 |
| 用户名 | 镜像仓库用户名 |
| 密码 | 镜像仓库密码（**不是账号登录密码**） |

#### ⚠️ 避坑 5：凭证地址必须包含命名空间

**现象**：

```
failed to push <...>/pm-frontend:latest: push access denied,
repository does not exist or may require authorization:
server message: insufficient_scope: authorization failed
```

**原因**：插件拼出的镜像名是 `<凭证里的地址>/<仓库名>:<标签>`，
**它不会自动补命名空间**。而 ACR 的路径必须是 `<端点>/<命名空间>/<仓库名>`。

**修法**：把「docker仓库地址」写成：

```
crpi-xxxxxxxx.cn-<地域>.personal.cr.aliyuncs.com/<命名空间>
```

**判别口诀**：同一个仓库、同一条凭证，**基础镜像拉得动、成品镜像推不动**
⇒ 就是推送目标路径缺命名空间。

> **附带好处**：走凭证管理后，**仓库里只有凭证 ID，密码不落库** ✓
> 千万不要把密码写进流水线 YAML 的字段里 —— Gitee 编辑器会把内容原样写回仓库。

### 3.3 主机管理（注册服务器）

位置：**设置 → 流水线 Gitee Go → 主机管理 → 新建主机组**

1. 新建主机组，记下**主机组 ID**（如 `ali_cloudland`）
2. 按提示在服务器上执行安装命令，注册 Gitee Go runner
3. 注册成功后，把**主机的 UUID** 记下来（流水线里要用）

> **注意**：主机组是**账号级**的，同一账号下多个仓库可共用同一个主机组。

### 3.4 流水线 YAML

文件位置：**仓库根目录 `.workflow/<流水线名>.yml`**

```yaml
version: "1.0"
name: pm-system-deploy
displayName: pm-system-deploy

stages:
- name: 云端构建镜像
  displayName: 云端构建镜像
  strategy: naturally
  trigger: auto
  executor: []
  steps:
  - step: build@docker
    name: build_backend_image
    displayName: 构建后端镜像
    certificate: "<凭证ID>"                                   # 凭证管理里那条
    repository: "{{CERTIFICATION.<凭证ID>.server}}"            # ⚠️ 必须是 <凭证ID>，不是 ${CERTIFICATE}
    username: "{{CERTIFICATION.<凭证ID>.username}}"
    password: "{{CERTIFICATION.<凭证ID>.password}}"
    tag: pm-backend:latest
    dockerfile: ./backend/Dockerfile
    isCache: false
    processorType: [amd64]
    strategy: { retry: "0" }

  - step: build@docker
    name: build_frontend_image
    displayName: 构建前端镜像
    certificate: "<凭证ID>"
    repository: "{{CERTIFICATION.<凭证ID>.server}}"
    username: "{{CERTIFICATION.<凭证ID>.username}}"
    password: "{{CERTIFICATION.<凭证ID>.password}}"
    tag: pm-frontend:latest
    dockerfile: ./frontend/Dockerfile
    isCache: false
    processorType: [amd64]
    strategy: { retry: "0" }

- name: 部署到阿里云主机
  displayName: 部署到阿里云主机
  strategy: naturally
  trigger: auto
  # ⚠️ 质量门禁：必须等构建成功才部署（编辑器会删掉它，务必核对）
  dependsOn:
  - 云端构建镜像
  executor:
  - <Gitee 用户名>
  steps:
  - step: shell@agent
    name: deploy_aliyun
    displayName: 执行部署脚本
    schedulerType: DISTRIBUTED
    scriptType: SH
    script: |-
      set -Eeuo pipefail

      APP_DIR="/root/pm-system"
      BRANCH="main"
      REPO_URL="<仓库 HTTPS 地址>"

      if [ ! -d "$APP_DIR/.git" ]; then
        echo ">> 首次部署：克隆仓库到 $APP_DIR"
        mkdir -p "$(dirname "$APP_DIR")"
        git clone -b "$BRANCH" "$REPO_URL" "$APP_DIR"
      fi

      cd "$APP_DIR"
      git fetch origin "$BRANCH"
      git checkout "$BRANCH"
      git reset --hard "origin/$BRANCH"

      /bin/bash scripts/deploy.sh "$BRANCH"
    gitClone: "false"
    hostGroupID:
      ID: <主机组ID>
      hostID:
      - <主机UUID>          # ⚠️ 不能留空数组，留空会报"找不到主机实例"
    notify: []
    strategy: { retry: "0" }

triggers:
  trigger: auto
  push:
    branches:
      precise: [main]
notify: []
```

#### 关键字段说明

| 字段 | 说明 |
|---|---|
| `build@docker` | 镜像构建插件，底层是 **buildctl（无守护进程）**，**不需要 Docker-in-Docker** |
| `certificate` | 凭证 ID，来自凭证管理 |
| `repository` / `username` / `password` | **必须是 `{{CERTIFICATION.<凭证ID>.*}}` 模板**，写死字面值不生效 |
| `tag` | 只写 `<仓库名>:<标签>`，命名空间由 `repository` 提供 |
| `isCache` | `false` = 不使用构建缓存（社区反馈开启缓存会报权限错误） |
| `shell@agent` + `hostGroupID` | 在自有主机上执行脚本，需指定主机组与主机 UUID |
| `dependsOn` | 值是**阶段（stage）的 `name`**，不是 `displayName` |

#### ⚠️ 避坑 6：`repository` / `username` / `password` 必须是凭证模板

**现象**：插件日志里打印出**未解析的模板**，随后推送失败：

```
DOCKER_REPOSITORY={{CERTIFICATION.${CERTIFICATE}.server}}
error: failed to solve: ... {{CERTIFICATION...}}/pm-backend:latest
```

**原因**：`${CERTIFICATE}` 不是运行时变量，**必须在编辑器保存时被替换成凭证 ID**。
写死的字面地址/账号/密码也不生效。

**修法**：**用图形视图配置**（选中凭证），编辑器会生成正确形式。
但要**逐个核对每个构建步骤** —— 编辑器对不同步骤可能行为不一致
（本项目就出现过「后端已代入、前端未代入」）。

> **通用判别法**：凡「照文档写了却行为不符」，
> **先去看插件打印的原始参数**。出现未解析模板或空值 = 字段没被读到。

#### ⚠️ 避坑 7：可视化编辑器会重写整个 YAML 文件

**这个坑极其危险，本项目已踩两次。**

编辑器保存时会：
- **删掉所有注释**
- 重排格式、把 stage `name` 改成中文
- **删掉 `dependsOn`** ⇒ **构建失败也会照常执行部署，质量门禁失效**

**应对**：

> **改流水线优先改仓库里的 YAML 并 push。**
> **万不得已用网页编辑器，保存后必须回仓库核对 `dependsOn` 是否还在：**
> ```bash
> git fetch origin main
> git show FETCH_HEAD:.workflow/<流水线文件>.yml | grep -A2 dependsOn
> ```

## 4. 阿里云侧配置

### 4.1 安全组（放行对外端口）

**必须做**，否则服务正常但外网访问不了。

阿里云控制台 → ECS → 安全组 → 配置规则 → 入方向 → 手动添加：

| 配置项 | 值 |
|---|---|
| 协议类型 | 自定义 TCP |
| 端口范围 | `8081/8081` |
| 授权对象 | 自己的公网 IP `/32`（更安全），或 `0.0.0.0/0`（对所有人开放） |

**排障三板斧**（区分「应用问题」与「网络问题」）：

```bash
curl -I http://127.0.0.1:8081     # ① 本机测，绕过所有防火墙 → 通说明应用正常
ss -ltnp | grep 8081             # ② 确认 0.0.0.0:8081 在监听
# ③ 从自己电脑浏览器访问 http://<公网IP>:8081
#    ①② 通、③ 不通 → 就是安全组（Docker 已绕过 host 防火墙）
```

### 4.2 容器镜像服务 ACR

1. **开通**：控制台搜「容器镜像服务 ACR」→ 开通**个人版**（免费）
2. **新建命名空间**：名称**必须与 Gitee 个人空间地址一致**（本项目为 `t1longlive`）
3. **设置访问凭证**：ACR → 访问凭证 → 设置**固定密码**
   （这是**独立于阿里云账号密码**的仓库专用密码）
4. 记下**实例端点**，形如 `crpi-xxxxxxxx.cn-<地域>.personal.cr.aliyuncs.com`

> 端点格式注意：新版个人版是 `<实例ID>.<地域>.personal.cr.aliyuncs.com`，
> **不是**老版通用域名 `registry.cn-<地域>.aliyuncs.com`。以控制台显示为准。

### 4.3 服务器准备

#### ① 安装 Docker + Compose

```bash
docker --version && docker compose version
```

#### ② 配置 Docker 镜像源（**关键，否则拉不到基础镜像**）

```bash
vi /etc/docker/daemon.json
```

```json
{
  "registry-mirrors": ["<可用的镜像加速地址>"]
}
```

```bash
systemctl daemon-reload && systemctl restart docker
docker info | grep -A3 'Registry Mirrors'
docker pull hello-world            # 验证
```

> **避坑**：镜像源列表里**只保留可用源**。
> Docker 是「按顺序逐个尝试，失败才跳下一个」，
> 混着已停服的源虽然最终仍能成功，但每次拉取都要白等前面的超时。

#### ③ 登录私有镜像仓库

```bash
docker login <ACR端点>
# 输入 ACR 的固定密码
```

凭据会存到 **root 的 `~/.docker/config.json`**。
部署脚本由 Gitee agent 以 root 执行（`$HOME=/root`），路径一致。

#### ④ 创建部署目录与 `.env`

```bash
mkdir -p /root/pm-system
cd /root/pm-system
cp .env.example .env
vi .env                       # 填真实值
chmod 600 .env
docker compose config | head -30   # 语法自检
```

### 4.4 `.env` 怎么填

| 变量 | 要改吗 | 说明 |
|---|---|---|
| `DB_PASSWORD` | **✅ 改** | **同时**是 MySQL root 密码、后端连接密码、healthcheck 密码 |
| `REDIS_PASSWORD` | **✅ 改** | |
| `JWT_SECRET` | **✅ 改** | 默认值写在公开仓库里 = 没有密钥。**必须 ≥32 字符** |
| `SQL_LOG_IMPL` | 建议改 | 生产应关闭 SQL 打印（`NoLoggingImpl`） |
| `DB_URL` | ⛔ 别动 | 主机名是 **compose 服务名** `mysql`，改成 localhost 会连不上 |
| `REDIS_HOST` | ⛔ 别动 | 同上，服务名 `redis` |
| `PM_UPLOAD_DIR` | ⛔ 别动 | 必须与 compose 具名卷挂载点一致 |
| `CORS_ALLOWED_ORIGINS` | 通常不用改 | 若 nginx 用了 `$http_host` 则 CORS 不参与；**切勿填 `*`** |

#### ⚠️ 避坑 8：密码里的特殊字符会被吃掉

- `#` 是注释符 → 后面的内容被截断
- `$` 会触发 compose 变量插值

**最稳妥：用纯十六进制随机串**

```bash
openssl rand -hex 16      # 数据库/Redis 密码（只含 0-9a-f）
openssl rand -base64 48   # JWT 密钥（≥32 字符）
```

#### ⚠️ 避坑 9：密码必须在「首次成功启动之前」定稿

**MySQL 只在数据目录为空时读取密码做初始化。**
一旦卷里已有数据，改 `.env` **不会**同步到库里，表现为后端连不上、healthcheck 一直失败。

顺序必须是：

```
cp .env.example .env  →  改密码  →  首次 up -d
```

若容器已起过，需清卷重来：

```bash
docker compose down
docker volume rm <项目名>_pm-mysql-data    # ⚠️ 删卷 = 删库！
```

### 回滚

当前镜像 tag 固定为 `latest`，**无法回滚到指定版本**。
若要支持回滚，需改进：

- 把 tag 改成 `${GITEE_PIPELINE_BUILD_NUMBER}` 或 commit SHA
- 部署时通过环境变量传入要部署的 tag
- 回滚 = 重新部署旧 tag 的镜像

## 7. 排错手册

### 7.1 构建阶段

| 现象 | 原因 | 修法 |
|---|---|---|
| `npm: command not found` / `mvn: command not found`，且报错来自插件自身脚本 | 工具链版本没命中 Gitee 预置清单 | 用网页编辑器的**版本下拉框**选值（唯一权威来源） |
| 日志中 `start exec` 与 `end exec` 之间**空白** | 字段名不被识别，命令被静默跳过 | 对照插件文档核对字段名 |
| `DOCKER_REPOSITORY={{CERTIFICATION...}}` | 凭证未选中，或用了 `${CERTIFICATE}` 未代入形式 | 图形视图重新选中凭证；核对生成的模板 |
| `dial tcp ...: i/o timeout`（registry-1.docker.io） | **Gitee 云端无法访问 Docker Hub** | 基础镜像转存到自己的 ACR，改 Dockerfile 的 `FROM` |
| `insufficient_scope: authorization failed` + `repository does not exist` | 推送目标缺命名空间 | 凭证的「docker仓库地址」改成 `<端点>/<命名空间>` |
| `there is no POM in this directory` / `cd: xxx: No such file` | 构建任务工作目录是**仓库根**，项目在子目录 | `commands` 里先 `cd backend` / `cd frontend` |
| `nothing to compress` | `artifacts.path` 指向的目录不存在 | 核对路径；路径以**仓库根**为基准 |
| `Cannot iterate over string` | `artifacts.path` 写成了字符串 | 改成 YAML 列表 |

### 7.2 部署阶段

| 现象 | 原因 | 修法 |
|---|---|---|
| `No matching host instance was found under host group xxx` | `hostGroupID.hostID` 为空数组 | 补上具体的主机 UUID |
| `Another deployment is already running` | `flock` 并发保护生效（**不是 bug**） | 等前一次跑完 |
| `ERROR: .env not found` | 服务器上没建 `.env` | 见 4.4 |
| 部署日志在某一步**突然中断、无任何报错** | 进程被 OOM Killer 杀掉 | 查 `dmesg -T \| grep -i oom`；加内存或改用 Push 模型 |
| `Authentication failed` on pull | 服务器未 `docker login` 或密码已轮换 | 重新 `docker login <ACR端点>` |

### 7.3 运行阶段

| 现象 | 原因 | 修法 |
|---|---|---|
| 容器 Up，但浏览器打不开 | **安全组未放行端口** | 见 4.1 |
| `POST /api/**` 全部 403（不是 401） | nginx 用了 `$host`（丢端口）→ 同源被判为跨域 | 改成 `$http_host` |
| 后端启动即崩、反复重启 | 库里没有表 | 把 `init.sql` 挂进 `/docker-entrypoint-initdb.d/`，并清卷重来 |
| 启动报 `Circular placeholder reference` | 配置里属性名与占位符同名 | 删掉那行，默认值写在 `@Value` 里 |
| 容器内正常、本地 IDE 起不来 | 环境不对称（容器注入了环境变量） | 见避坑 1 / 2 |
| 改了 `.env` 密码但不生效 | MySQL 只在首次初始化读密码 | 清卷重来 |

## 8. 交付清单

改造一套项目需要「定义 / 修改 / 添加」的东西，按类别汇总：

### 8.1 项目里要**添加**的文件

| 文件 | 作用 |
|---|---|
| `backend/Dockerfile` | 后端多阶段镜像 |
| `frontend/Dockerfile` | 前端多阶段镜像 |
| `backend/.dockerignore`、`frontend/.dockerignore` | 减小构建上下文 |
| `docker-compose.yml` | 编排 |
| `frontend/nginx.conf` | 静态托管 + `/api` 反代（`$http_host`！） |
| `.env.example` | 环境变量模板（与 application.yml 一一对应） |
| `.gitattributes` | 钉死 `eol=lf` |
| `scripts/deploy.sh` | 服务器端部署脚本 |
| `scripts/mirror-base-images.sh` | 基础镜像转存 ACR |
| `.workflow/<流水线名>.yml` | Gitee 流水线定义 |
| `settings.xml` | 国内 Maven 镜像加速 |

### 8.2 项目里要**修改**的

| 位置 | 改什么 |
|---|---|
| `application.yml` | 所有环境相关配置改成 `${ENV:default}` |
| `.gitignore` | 排除 `.env`、`.env.local`，保留 `!*.env.example` |
| 读配置的 Java 类 | 用 `@Value("${X:default}")` 读取，**不要在 yml 里定义同名键** |

### 8.3 Gitee 上要做的

1. 开通流水线（需绑定手机号）
2. **凭证管理**新建 Docker 凭证（地址含命名空间）
3. **主机管理**新建主机组 / 注册 runner，记下主机组 ID 与主机 UUID
4. 流水线里给每个构建任务选中凭证
5. push 触发自动部署

### 8.4 阿里云上要做的

1. **安全组**放行对外端口
2. **ACR**：开通、建命名空间（与 Gitee 空间地址一致）、设仓库密码
3. **服务器**：配置 Docker 镜像源、`docker login`、建目录与 `.env`
4. 转存 4 个基础镜像到 ACR

### 8.5 一次性 vs 每次

| 一次性 | 每次部署 |
|---|---|
| 安全组、ACR、命名空间、仓库密码 | push 代码 |
| Docker 镜像源配置、`docker login` | （其余全自动） |
| 基础镜像转存 | |
| 主机组注册、凭证创建、流水线配置 | |
